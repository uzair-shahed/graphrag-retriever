# GraphRAG Output Schemas

**Last modified:** 18 October 2026

**Purpose of this file:**
Document the structured-output schemas used by the MuSiQue GraphRAG project for Ollama-backed extraction and answer generation, including where each schema is defined, how it is sent to Ollama, and what validation remains necessary after generation.

**Files that use this file:**
The Ollama JSON Schema adapter, the answer and extraction LLM factories, their tests, and future work on GraphRAG generation contracts should use this note as the schema reference.

**Caveats:**
The exact extraction schema is generated by the installed `neo4j-graphrag` Pydantic model and can change with that dependency. JSON Schema constrains response shape, not factual correctness, graph referential integrity, evidence coverage, or answer grounding. Continue validating outputs in GraphRAG and in application code.

## Overview

The Ollama-backed generation paths use two different Pydantic models and therefore two different JSON Schemas:

| Purpose | Pydantic model | Definition / configuration |
|---|---|---|
| Knowledge graph extraction | `neo4j_graphrag.components.types.Neo4jGraph` | Configured as the extraction response model in `src/graphrag_pipeline/extraction/pipeline.py` |
| Grounded question answering | `graphrag_pipeline.answer.GeneratedAnswer` | Defined and configured in `src/graphrag_pipeline/answer.py` |

`src/graphrag_pipeline/ollama_json_schema.py` converts a response model to a schema with `model_json_schema()`. The adapter passes that schema to Ollama's chat endpoint through its top-level `format` argument for both synchronous and asynchronous calls. `response_model` configures the adapter's default schema; it is not itself an Ollama request parameter.

OpenRouter follows its separate GraphRAG/OpenAI-compatible path. This note describes the Ollama schema adapter.

## Extraction Schema

`Neo4jGraph` is the extraction response model used by GraphRAG's `LLMEntityRelationExtractor`. Its conceptual JSON shape is:

```json
{
  "nodes": [
    {
      "id": "0",
      "label": "Person",
      "properties": {
        "name": "Alice"
      },
      "embedding_properties": {}
    }
  ],
  "relationships": [
    {
      "start_node_id": "0",
      "end_node_id": "1",
      "type": "FOUNDED",
      "properties": {},
      "embedding_properties": {}
    }
  ]
}
```

`nodes` and `relationships` are required arrays. Each node requires string `id` and `label`; each relationship requires string `start_node_id`, `end_node_id`, and `type`. The generated model schema forbids undeclared fields on the graph, node, and relationship objects. This is what excludes misspelled or alternate endpoint keys such as `start_node` or `end_node`.

The ontology remains intentionally open: node labels, relationship types, and keys in the `properties` maps are not enumerated. Property values are restricted to Neo4j-compatible primitive, temporal, list, or geographic values. This lets the extractor represent MuSiQue's varied subject matter while enforcing the graph wire format. `embedding_properties` is also a string-keyed map of float arrays.

The model is defined by GraphRAG, not this repository. The installed package version in the current project environment is `neo4j-graphrag` 1.21.0. The authoritative runtime schema is:

```python
from neo4j_graphrag.components.types import Neo4jGraph

schema = Neo4jGraph.model_json_schema()
```

### Extraction request path

`src/graphrag_pipeline/extraction/pipeline.py` configures `OllamaJSONSchemaLLM` with `response_model=Neo4jGraph`. GraphRAG detects the adapter's `supports_structured_output = True` and calls its async LLM interface with `response_format=Neo4jGraph`. The adapter resolves that model to `Neo4jGraph.model_json_schema()` and sends it as `format=<schema>` to Ollama. GraphRAG then validates the returned content as `Neo4jGraph` before graph post-processing and persistence.

The pipeline's `schema="FREE"` controls graph ontology guidance; it is separate from the response JSON Schema. `FREE` allows varied labels and relationship types, while the `Neo4jGraph` response schema still requires the structural fields shown above.

## Answer Schema

`GeneratedAnswer` is the application's answer response model:

```json
{
  "answer": "Alice founded Acme Corporation.",
  "citations": ["musique:record-1:paragraph:0"]
}
```

Its Pydantic definition in `src/graphrag_pipeline/answer.py` requires:

- Exactly the `answer` and `citations` fields; extra fields are forbidden.
- `answer` is a non-empty strict string.
- `citations` is a non-empty array of strict strings.

The set of valid citation values is dynamic for each request, so it is not encoded as a fixed enum in the schema. After parsing, the answer boundary checks that citations refer to retrieved chunk IDs and removes duplicate IDs while preserving order. The schema does not determine whether the answer is supported by the cited text; that remains a grounding/evaluation responsibility.

### Answer request path

`src/graphrag_pipeline/answer.py` configures `OllamaJSONSchemaLLM` with `response_model=GeneratedAnswer`. For VectorRAG, the answer boundary passes the generic JSON response hint; the adapter maps that hint to its configured `GeneratedAnswer` schema and sends it in Ollama's top-level `format` field. For GraphRAG, the managed `GraphRAG.search()` call invokes the same adapter with its prompt and the adapter's default schema. The application then parses and validates the returned answer using `GeneratedAnswer` and checks citation membership.

## Validation Boundaries

Structured output and validation serve complementary purposes:

1. Ollama's native `format` schema constrains the model's response structure during generation.
2. GraphRAG validates extracted output against `Neo4jGraph` before it writes extracted entities and relationships.
3. The application's answer boundary validates the response against `GeneratedAnswer` and rejects citations outside retrieved evidence.
4. MuSiQue correctness verification compares returned evidence against the source record and reports supporting-paragraph coverage separately.

A schema-conforming response can still contain unsupported or incorrect facts, invalid node references, weak extractions, or an answer unsupported by its citations. Do not treat successful JSON Schema generation as a substitute for these post-generation checks.

## Tests

- `tests/unit/test_ollama_json_schema.py` verifies that synchronous and asynchronous adapter calls send the configured schema as Ollama's top-level `format` parameter and validate representative output.
- `tests/integration/test_ollama_integration.py` exercises the configured Ollama model against both the answer and extraction schemas when the service and models are available.
- `tests/unit/test_answer.py` and `tests/unit/test_pipeline.py` verify that the correct response model is configured for each Ollama path.
